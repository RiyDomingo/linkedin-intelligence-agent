# li-ideas

Read [the shared context and approval contract](../li-context/references/context-contract.md) first.

Read only relevant projects, audience, public claims, recent user events and
history; apply li-history including available performance. If inputs are thin,
ask for recent work or propose evidence-gathering prompts, not invented milestones.
Use existing li-research findings or research only a question that materially helps.
For each worthwhile idea identify topic, specific angle, why it matters, target
reader, source/evidence needed, claim risks and overlap with earlier posts. Explain
what makes the angle different. Prefer fewer grounded ideas to a generic ten-item
list. Missing evidence is a task to gather, not an assumed achievement. Hand chosen
ideas to li-post/plan without drafting everything automatically.

Apply [li-read](../li-read/SKILL.md) when network or current activity context exists.
Evaluate current projects, recent events, network/research signals, public evidence,
audience relevance and fatigue. Prefer up to three strong distinct ideas. Each must
include topic, angle, WHY NOW, target reader, evidence available, evidence missing,
prior-post overlap and recommended format. Recommend a stronger option only with a
stated evidential reason. No meaningful idea is a valid outcome for thin material.

Request industry changes or community questions only when projects and content memory leave a useful information gap.
Delegate that public information need to [li-research](../li-research/SKILL.md),
using the shared contract and preserving evidence IDs.
